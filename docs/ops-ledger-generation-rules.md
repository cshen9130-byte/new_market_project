# FOF底层申赎台账生成规则

估值表生成的台账是**待核对底稿**。字段优先级永远是：

1. **交易确认单**（最准）
2. 母基金估值表上该底层的**数量 / 成本 / 行情**变动（次选）
3. 不得用确认日市值或确认日行情去反推申购净额、单位净值

同一母基金同一天只使用**一份**估值表。同一附件被入库两次、或估值日差一天的副本，不得把数量/成本加总；否则会把一笔申购算成两笔，再在次日「赎回」多出来的那一半。

日期、科目名称、邮件标题在不同托管/产品上会略有差别，但时间顺序和字段含义与下面金舆追风1号例子相同。

---

## 1. 权威来源：确认单优先

只要能匹配到该笔 FOF × 底层 的确认单，台账必须用确认单上的值，**不要用估值表算出来的金额/净值覆盖它**。

| 台账字段 | 确认单字段（本例：招商） | 本例真值 |
|---|---|---|
| FOF基金 / 备案号 | 委托人名称、证件号码 | 金舆追风1号 / SCJ536 |
| 底层基金 / 备案号 | 产品名称、产品代码 | 六妙星九紫二号 / SBUW51 |
| 交易类型 | 文件名/标题（申购确认单、赎回确认单…） | 申购 |
| **申请日期** | 申请日期 | **2026-08-06** |
| **确认日期** | 确认日期 | **2026-08-07** |
| **确认净额** | 确认金额（或申请金额；本例均为 1,000,000.00） | **1,000,000.00** |
| **确认份额** | 确认份额 | **895,175.01** |
| **确认单位净值** | 单位净值 | **1.1171** |
| 交易费用 | 交易费 | 0.00 |
| 来源 | — | `估值表+确认单` |
| 确认单附件 | 原 PDF | 可预览/下载 |

核对恒等式（申购）：

```
确认份额 × 确认单位净值 ≈ 确认净额
895,175.01 × 1.1171 = 999,999.99 ≈ 1,000,000.00
```

单位净值是**申请日（T）行情**，不是确认日（T+1）估值表上的行情。

**确认净额几乎总是整数金额。** 管理人申购/赎回习惯按整数下单（常见 10 万、50 万、100 万）。若同时出现两个候选净额，一个带零碎小数、一个是整元（尤其整万/整十万），选整数那个。本例 `1,010,831.62` vs `1,000,000.00` → **1,000,000.00**。份额可以有小数；不要把「净额也必须有小数」当成对的。

## 2. 邮件到达顺序（本例，预期模式）

三份材料都来自托管/TA 邮箱，**不是同一封、也不是同一天到达**。

| 顺序 | 文件（业务日） | 实际收到 | 说明 |
|---|---|---|---|
| 1 | 母基金估值表 **2026-08-06** | **2026-08-07 13:02** | 估值日后 **下一个工作日中午** 左右 |
| 2 | 底层→该 FOF 的 **申购确认单**（确认日 2026-08-07） | **2026-08-07 15:44** | 确认当日下午；附件经常是 **zip 内 PDF** |
| 3 | 母基金估值表 **2026-08-07** | **2026-08-10 12:22** | 再下一个工作日中午；**2026-08-08、08-09 周末不发** |

因此：

- 不能要求「确认单和确认日估值表同一封邮件」。
- 确认单可能比确认日估值表 **早到几天**（本例早到一个周末）。
- 估值表 T 日文件，邮箱日期往往是 T+1（遇周末/节假日则到下一工作日）。
- 必须解压 **zip 里的确认单 PDF**。当前实现只认 `.pdf/.xlsx` 文件名，**不拆 zip**，所以本例确认单未入库，台账才退化成纯估值表估算。

确认单文件名常见形态（托管不同会变，关键词仍是「确认单/确认函」）：

```
{底层产品名}_{FOF产品名}_{申请日yyyyMMdd}_{流水号}_申购确认单.pdf
```

本例：

`六妙星九紫二号私募证券投资基金_金舆追风1号私募证券投资基金_20260806_151628053_申购确认单.pdf`

邮件主题常见：`{FOF名}{YYYYMMDD}TA确认单数据`，附件可能是 zip。

## 3. 估值表怎么用（确认单缺失时的正确算法）

用**相邻两个估值日**同一底层（科目代码含备案号，如 `1108.02.01.SBUW51 OTC`）的明细，不要用市值差。

本例科目行：

| 估值日 | 数量 | 成本 | 行情 | 市值 |
|---|---:|---:|---:|---:|
| 2026-08-06（申请日 T） | 860,955.66 | 1,000,000.00 | **1.1171** | 961,773.57 |
| 2026-08-07（确认日 T+1） | 1,756,130.67 | 2,000,000.00 | 1.1292 | 1,983,022.75 |

份额有变动时：

| 台账字段 | 估值表算法 | 本例 |
|---|---|---|
| 申请日期 | **变动前那个估值日 T**（数量尚未增加的那天） | 2026-08-06 |
| 确认日期 | **数量已经增加的估值日 T+1** | 2026-08-07 |
| 确认份额 | `数量(T+1) − 数量(T)` | 1,756,130.67 − 860,955.66 = **895,175.01** |
| 确认净额 | **`成本(T+1) − 成本(T)`**（申购为正、赎回取绝对值） | 2,000,000 − 1,000,000 = **1,000,000.00** |
| 确认单位净值 | **申请日 T 的行情**，不是 T+1 行情 | **1.1171** |
| 交易类型 | 数量增加→申购；减少→赎回（确认单业务类型可覆盖） | 申购 |

备用校验（接近即可）：

```
确认份额 × T日行情 ≈ 确认净额
895,175.01 × 1.1171 ≈ 1,000,000
```

选净额时：Δ成本、确认单金额、份额×T日行情 应对上同一个整数；`Δ份额 × T+1行情` 得到的带小数金额（本例 1,010,831.62）应丢弃。优先整元，其次整百/整千/整万。

### 禁止（本例曾经算错的做法）

| 错误做法 | 本例错误结果 | 为什么错 |
|---|---|---|
| 申请日 = 确认日 = 数量跳变当天 | 都写成 2026-08-07 | 申请发生在前一估值日 |
| 确认单位净值 = 跳变当天行情 | 1.1292 | 那是 T+1 市价，不是申购确认净值 |
| 确认净额 = Δ份额 × T+1 行情 | 1,010,831.62 | 把旧份额的涨跌也算进申购款了 |
| 确认净额 = Δ市值 | 1,021,249.18 | 含浮盈浮亏，不是申购净额 |

市值差、T+1 行情只用于持仓估值，**不能**当作申赎确认金额/净值。

## 4. 匹配确认单到估值表变动

在份额变动（估值日 = T+1）上找确认单：

1. 底层产品代码/备案号家族一致（本例 SBUW51）。
2. 投资人/委托人是该母 FOF（名称或备案号 SCJ536）。
3. 确认单 **确认日期 ≈ T+1**，**申请日期 ≈ T**（允许因节假日错几天）。
4. 确认份额与 `Δ数量` 接近（本例完全相等）。
5. 业务类型与份额增减方向一致（申购/赎回）。

命中后：**日期、净额、净值、费用、附件全部改用确认单**；份额若两边一致则用确认单。

未命中才走第 3 节估值表算法，来源记 `估值表`，状态 **待确认**。

---

## 5. 工作日与节假日

- 估值表、确认单按**基金交易日**，不是自然日连发。
- 周五估值表常周一中午到；节假日顺延 1～2 个工作日。
- 「相邻估值日」指该产品估值表上**实际出现的上一日期**，不是日历昨天。
- 申请日、确认日不要用**邮件收到时间**，用文件/确认单上的业务日期。

---

## 6. 实现时必须做到的事

1. 邮箱抓取：主题或附件名含「确认单/确认函」时，**解开 zip，取出其中 PDF** 再解析入库。
2. 生成台账：先匹配 `ops_email_confirm_records`，命中则整行用确认单。
3. 估值表序列必须带 **数量、成本、行情**，不能只用数量+市值。
4. 无确认单时：申请日=T、确认日=T+1、净值=T日行情、净额=Δ成本。
5. 两个候选确认净额时优先**整数金额**（管理人按整数申赎）；带零碎小数的那个多半是用错了确认日行情。
6. 已确认 / 手工修正 / 指令行不得被自动覆盖。
7. 夜间 ETL 在 `email_nav_parse` + `investment_pool_metrics` 之后自动跑
   `ops_ledger_from_valuation`（`scripts/ma/ops_ledger_from_valuation_etl.ts`），
   把新的估值表份额变动和确认单写入 `ops_ledger_records`。页面上的「从估值表生成」仍可手工补跑。
8. 已清仓底层也要出历史申购/赎回。不要用「当前市值>0」过滤产品池，否则清仓后这两行会从台账消失。相邻母基金估值日上数量变为 0 即为赎回。
